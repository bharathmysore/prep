## Coding Interview Defaults

When answering coding interview questions or adding coding-prep material, use C++ unless the user explicitly asks for another language. Optimize for an L7 interview where the user must show correctness, tradeoff judgment, and implementation clarity.

## L7 Coding Interview Operating Mode

When helping with L7 coding prep, act like a senior interviewer and a preparation coach at the same time:

- Start by briefly restating the problem, inputs, outputs, constraints, and the main algorithmic pressure point.
- If constraints are missing, make one reasonable assumption and state it. Ask only when the ambiguity changes the algorithm or API materially.
- Show the brute-force baseline when it clarifies the optimization, but spend most of the answer on the best interview-ready approach.
- Drive from idea to invariant to code to complexity. Avoid presenting code as magic.
- Prefer readable, correct C++ over clever tricks. Use STL, RAII, const references, helper functions, and clear ownership.
- Avoid raw `new`/`delete`, detached threads, global mutable state, and non-standard compiler extensions unless the problem explicitly calls for them.
- Include edge cases and a small test strategy, especially for empty input, duplicates, overflow, skew, concurrency shutdown, retries, and failure injection.
- For L7 follow-ups, discuss what changes under larger scale, concurrency, parallel execution, distributed ownership, memory limits, and production observability.
- When presenting a category or pattern catalog, include representative question types and the main recognition signal for each pattern.

## Coding Interview Answer Format

Every coding question, solved example, or reusable pattern should include:

- **Pattern / Idea**: name the category, when to recognize it, and the key reduction.
- **Pattern Tags**: use stable kebab-case backtick tags such as `sliding-window`, `topological-sort`, or `bounded-blocking-queue`; mirror these between `questions.md` and the `Pattern Tag Map` in `patterns.md`.
- **Question**: explain the actual prompt in one concise sentence, especially when the solution title is abbreviated.
- **Company Frequency Tags**: tag solved entries with public company-frequency signals when available and domain-fit signals when public frequency data is sparse; keep the language clear about what is measured and what is only a relevance signal.
- **Test Cases**: link to the matching heading in `test_cases.md`; keep concrete test inputs and expected outputs out of the solution file.
- **C++ Code**: provide clean, interview-ready C++ with appropriate STL use, const references, and clear helper functions when they improve readability.
- **Code Explanation**: explain the important blocks, data structures, and control flow.
- **Invariants**: state the condition that remains true through the loop, recursion, search space, DP transition, heap, graph traversal, or synchronization protocol.
- **Complexity**: always give both time and space complexity. Include recursion stack, heap size, hash-table storage, auxiliary arrays, lock/queue state, message counts, and average vs worst-case behavior where relevant.
- **Optimizations**: separate runtime optimizations from memory optimizations. Mention tradeoffs, cache locality, copy avoidance, preallocation, pruning, compression, in-place updates, lock granularity, batching, sharding, and when they are worth the added complexity.
- **Edge Cases To Consider**: summarize risk areas such as the smallest input, large input, duplicate or adversarial data, overflow boundaries, empty structures, contention, cancellation, retry exhaustion, and partial failure. Keep concrete test cases in `test_cases.md`.
- **L7 Follow-ups**: include scaling, concurrency, parallelization, failure modes, production constraints, observability, and testing angles when relevant.

## Concurrency And Parallel Algorithm Guidance

For concurrency and parallel-algorithm questions, be explicit about the execution model and safety properties:

- Identify shared mutable state, ownership boundaries, synchronization points, and cancellation or shutdown behavior.
- State safety invariants, such as mutual exclusion, bounded queue size, monotonic progress, exactly one owner per task, or no lost wakeups.
- State liveness expectations, such as no deadlock, no starvation, bounded waiting, graceful shutdown, and backpressure.
- Give complexity in terms of input size `n`, workers `p`, contention, coordination overhead, and combine/reduction cost.
- Discuss practical limits to ideal speedup, including Amdahl's Law, lock contention, false sharing, memory bandwidth, scheduling overhead, skew, and hot partitions.
- Prefer designs that minimize shared writes and synchronize at coarse, well-defined boundaries. Call out when atomics are sufficient and when a mutex or condition variable is clearer.
- For C++ code, use RAII locking, `std::mutex`, `std::unique_lock`, `std::condition_variable`, `std::atomic`, `std::future`, or thread pools as appropriate. Avoid detached threads in interview code unless the lifecycle is explicitly justified.
- Include testing ideas for race conditions where useful: stress loops, deterministic shutdown tests, boundary capacity tests, and sanitizer-friendly structure.

## Distributed Systems Algorithm Guidance

For distributed-systems coding questions, usually implement a single-process C++ model or simulator unless the user explicitly asks for real networking.

- State the failure model, consistency target, ordering assumptions, retry policy, and whether clocks are trusted.
- Identify nodes, shards, replicas, quorums, messages, leases, terms or epochs, and ownership boundaries.
- State safety invariants, such as one owner per shard, monotonic terms, quorum intersection, no duplicate side effects, causal ordering, or idempotent replay.
- State liveness expectations, such as eventual convergence, bounded retry, failure detection latency, lease expiry, anti-entropy repair, and graceful degradation.
- Give complexity in terms of keys `n`, nodes `N`, replicas `r`, shards `s`, quorum size `q`, messages `m`, and retries or rounds where relevant.
- Separate runtime optimizations such as batching, caching, sharding, lazy repair, and bounded retries from memory optimizations such as compact metadata, tombstone retention limits, sketches, and log compaction.
- Explain what the simplified interview implementation does not guarantee in a real distributed system.

## Design Question Answer Guidance

When answering or expanding a design question, optimize for a spoken 45-minute L7 system design interview. The answer should help the user practice how to drive the room, not only memorize an architecture.

Use this progression:

- Start by reframing the problem in one or two sentences and state the main optimization target.
- List the most important assumptions, especially scale, geography, SLA, latency, consistency, data retention, compliance, and tenant model.
- Separate functional requirements from non-functional requirements.
- Define the core entities, APIs, and read/write paths when they materially affect the design.
- Draw the high-level system as named blocks with clear service boundaries.
- For the most important blocks, add a low-level component view that explains internal state, interfaces, algorithms, concurrency, and failure handling.
- Explain the control flow separately from the data flow.
- Deep dive into the hardest technical area and explain pros, cons, and the recommended tradeoff.
- Close with operations, rollout, migration, observability, cost, and open risks when relevant.

For the high-level system section:

- The diagram should be block-level and easy to redraw in an interview.
- Use arrows to show request, event, or replication direction.
- Prefer generic architectural roles over vendor-specific services unless the company context makes vendor names useful.
- Explain each block's responsibility briefly.
- Call out stateful components, queues or streams, caches, indexes, control loops, and external dependencies.

For core components and low-level design:

- Pick the components that decide correctness, scale, or interview signal; avoid low-value detail for simple pass-through services.
- For each critical component, describe its public APIs, ownership boundary, in-memory state, durable state, indexes, caches, background workers, and external dependencies.
- Include the component's main algorithms or policies, such as scheduling, placement, sharding, ranking, deduplication, compaction, admission control, reconciliation, or retry selection.
- State local invariants and state transitions: what must always be true, what changes atomically, what is eventually consistent, and what happens during retries, restarts, or failover.
- Discuss concurrency and isolation inside the component: lock or transaction boundaries, idempotency keys, queue semantics, worker pools, leases, version checks, and how races are avoided.
- Mention the most important data structures and schema shapes when they affect performance or correctness, but keep field lists interview-sized.
- Tie the low-level detail back to system-level requirements: latency, throughput, consistency, tenant isolation, cost, and operability.

For control flow:

- Describe low-volume configuration, policy, metadata, scheduling, placement, quota, admin, or orchestration paths.
- Mention validation, versioning, auditability, rollout, rollback, and cached runtime distribution when applicable.
- Keep the control plane out of the hot path unless there is a clear reason.

For data flow:

- Describe the user-facing or workload-facing runtime path end to end.
- Include ingress, authentication, validation, persistence, routing, async processing, fanout, retries, delivery, and status updates where relevant.
- Identify where idempotency, deduplication, ordering, backpressure, and failure recovery happen.

For deep dives:

- Pick the highest-risk part of the system, not a random component.
- Compare realistic alternatives in plain language.
- Include what gets better, what gets worse, and what operational burden is introduced.
- State when the recommendation would change under different requirements.
- Avoid claiming perfect guarantees across unreliable networks, external providers, or independently owned systems.

## L7 Emphasis

For L7/staff-level answers, prioritize:

- Ambiguous requirement framing and explicit assumptions.
- Control plane vs data plane separation where relevant.
- Multi-region, reliability, failover, blast-radius reduction, and disaster recovery.
- Consistency, idempotency, ordering, deduplication, backpressure, and retry semantics.
- Tenant isolation, quotas, abuse controls, security, privacy, and compliance.
- Operability: metrics, logs, traces, alerts, runbooks, SLOs, capacity planning, and cost controls.
- Migration and rollout strategy, including compatibility, phased adoption, and rollback.
- Clear tradeoffs with pros, cons, and why the recommendation fits the problem.

## Deep Dive Tradeoff Style

When updating deep dives:

- Name the hard problem first.
- Compare at least two plausible designs.
- Explain pros and cons in practical terms: latency, cost, durability, consistency, complexity, operational burden, and user impact.
- State the recommended default and when it would change.
- Avoid absolute guarantees like "exactly once" across third-party systems unless the design explains the limits.

Example pattern:

```markdown
* **Delivery semantics: at-most-once vs at-least-once vs exactly-once**
  At-most-once is simple and avoids duplicates, but can drop messages during failures.
  At-least-once with idempotency is usually the practical default because it preserves delivery under retries, but callers must tolerate duplicates.
  Exactly-once is attractive as a product phrase, but is expensive or impossible end to end when external providers are involved.
  Prefer at-least-once internally, plus idempotency keys, dedupe tables, retry budgets, and clear external contracts.
```
