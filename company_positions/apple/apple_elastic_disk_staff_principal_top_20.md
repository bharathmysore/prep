# Apple Elastic Disk Staff/Principal Top 20 Questions

This is a target-role prep sheet for Apple Staff/Principal interviews on a cloud-based Elastic Disk or storage infrastructure team. Ranking blends public Apple coding-frequency signals from the local C++ index with role-fit signals from the public Elastic Disk posting: replication, metadata, durability, repair, snapshots, low-latency data path, storage QoS, and cross-org platform leadership. It is not an official Apple question bank.

## Ranking Method

- **Coding public frequency** uses the existing Apple company-frequency index at [C++ Company Frequency Focus Index](../../coding/cpp/company_frequency.md#apple).
- **Coding question links** point to the canonical C++ question catalogs; the answer column links to exact implemented C++ solution headings. If a future company/position sheet needs a prompt that does not exist yet, add it to the appropriate `coding/cpp/<category>/questions.md` file and implement it in `solutions.md` before linking it here.
- **Design question links** point to canonical design prompts in the system-design guides. If a future company/position sheet needs a design prompt that does not exist yet, add it to the relevant company guide and the system-design question TOC before linking it here.
- **Design role fit** is ranked by relevance to the public Elastic Disk responsibilities, not by leaked or official interview frequency.
- **Best practice order** for this role: lead with storage design, then drill the high-frequency Apple coding patterns that map to storage systems.

## Top 20

| Rank | Type | Question | Solution / Strong Answer | Complexity | Perf Improvements | Tradeoffs |
| ---: | --- | --- | --- | --- | --- | --- |
| 1 | Design | [Design Elastic Disk / EBS-class block storage](../../system_design/apple_l7_system_design_prep.md#21-design-elastic-disk-ebs-class-block-storage). | Separate control plane from data plane. Use Volume API, placement planner, metadata store, frontend, shard leaders, replica storage nodes, repair workers, and snapshot manager. Writes carry epoch, checksum, offset, length, and idempotency ID; leaders replicate WAL records before ack. | Discuss latency, throughput, IOPS, replication factor, repair bandwidth, and metadata scale. | Keep global metadata off hot path; cache signed placement maps; pipeline replication; split hot volumes into shards. | Synchronous remote durability improves safety but raises tail latency; local sync plus async remote copy lowers latency but has bounded exposure. |
| 2 | Design | [Design replication and metadata for Elastic Disk](../../system_design/apple_l7_system_design_prep.md#22-design-replication-and-metadata-for-elastic-disk). | Use a strongly consistent metadata store for volume/shard membership, epochs, attachment leases, and placement maps. Use leader-based shard replication with fencing and versioned membership changes. | Metadata ops `O(consensus quorum)`; write path `O(replica count)` messages. | Batch fsync, per-core queues, leader-local ordering, non-voting catch-up replicas. | Per-volume consensus is simpler; per-shard consensus scales better but adds operational complexity. |
| 3 | Design | [Design point-in-time snapshots and fast restore](../../system_design/apple_l7_system_design_prep.md#23-design-point-in-time-snapshots-and-volume-restore). | Use snapshot barriers at shard log indexes, changed-block tracking, immutable manifests, checksum-protected block references, and lazy restore with hydration workers. | Snapshot metadata proportional to changed extents; restore reads may be `O(remote block fetch)` until hydrated. | Incremental snapshots, content-addressed blocks, prefetch hot ranges, parallel hydration. | Lazy restore gives fast attach but first-read latency; eager restore is predictable but slower to start. |
| 4 | Design | [Design continuous scrubbing and automated repair](../../system_design/apple_l7_system_design_prep.md#24-design-continuous-scrubbing-and-automated-repair). | Store per-block, WAL, extent, and metadata checksums. Run local scrubbers, aggregate health, prioritize risky shards, quarantine bad replicas, and repair only from verified sources. | Scrub cost proportional to scanned bytes; repair cost proportional to missing/corrupt extents. | Token-bucket scrub throttling, risk-based scan cadence, repair coalescing, local-source preference. | Aggressive scrubbing finds issues earlier but competes with foreground I/O. |
| 5 | Coding | [LRU Cache](../../coding/cpp/advanced_data_structures/questions.md). | Solution: [implemented C++](../../coding/cpp/advanced_data_structures/solutions.md#1-lru-cache). Use `unordered_map<key, list::iterator>` plus doubly linked list ordered by recency; on get/put move node to front; evict from back. | Time `O(1)` average get/put; space `O(capacity)`. | Preallocate map/list nodes where possible; avoid copying large values; shard cache under concurrency. | Hash maps have adversarial worst cases; exact LRU is more expensive than approximate LRU in very hot systems. |
| 6 | Coding | [Concurrent Token Bucket](../../coding/cpp/concurrency/questions.md). | Solution: [implemented C++](../../coding/cpp/concurrency/solutions.md#3-concurrent-token-bucket). Under a mutex, lazily refill tokens from monotonic elapsed time; allow request if `tokens >= cost`, then decrement. | Time `O(1)`; space `O(1)`. | Lazy refill avoids background thread; per-tenant sharding reduces lock contention. | Single-node limiter is simple; distributed limits need shared counters, leases, or quota partitioning. |
| 7 | Coding | [Heartbeat Failure Detector](../../coding/cpp/distributed_systems_algorithms/questions.md). | Solution: [implemented C++](../../coding/cpp/distributed_systems_algorithms/solutions.md#4-heartbeat-failure-detector). Maintain `lastSeen[node]`; heartbeat updates timestamp; suspicion sweep returns nodes older than timeout. | Heartbeat `O(1)` average; sweep `O(n)`; space `O(n)`. | Min-heap by expiry avoids full sweeps; adaptive timeout reduces false positives. | Fast detection increases false positives; slow detection delays repair/failover. |
| 8 | Coding | [Top K Frequent Words / Elements](../../coding/cpp/heaps_ordered_structures/questions.md). | Solution: [implemented C++](../../coding/cpp/heaps_ordered_structures/solutions.md#6-top-k-frequent-words). Count frequencies with hash map, then keep size-`k` heap ordered by frequency and tie-breaker, or bucket sort if frequencies are bounded. | Heap approach `O(n log k)` time, `O(u + k)` space. | Use `nth_element` for one-shot top-k; reserve hash map; parallel count by partition then reduce. | Heap is memory-light; bucket sort can be faster but uses more memory and depends on count range. |
| 9 | Coding | [Parallel Top K](../../coding/cpp/parallel_algorithms/questions.md). | Solution: [implemented C++](../../coding/cpp/parallel_algorithms/solutions.md#4-parallel-top-k). Partition input, compute local top-k per worker, merge local candidates with a global heap or selection. | `O((n/p) log k + pk log k)` work shape; space `O(pk)`. | Local aggregation reduces global contention; use work stealing for skew. | Parallelism helps large data; overhead hurts small inputs; merge phase can bottleneck. |
| 10 | Coding | [Word Break](../../coding/cpp/dynamic_programming/questions.md). | Solution: [implemented C++](../../coding/cpp/dynamic_programming/solutions.md#7-word-break). Dynamic programming where `dp[i]` is true if prefix `s[0:i]` can be segmented; test previous cut points against dictionary. | Time `O(n^2 * substring cost)`; space `O(n)`. | Trie avoids substring allocation; limit max word length; use rolling hashes carefully. | DP is robust; trie is faster for many prefixes but adds implementation complexity. |
| 11 | Coding | [Merge Intervals](../../coding/cpp/arrays_strings/questions.md). | Solution: [implemented C++](../../coding/cpp/arrays_strings/solutions.md#5-merge-intervals). Sort intervals by start; scan and merge when next start is `<= current end`. | Time `O(n log n)`; space `O(1)` extra if sorting in place. | If input already sorted, reduce to `O(n)`; normalize intervals first. | Sorting dominates; preserving original order requires extra metadata. |
| 12 | Coding | [Min Stack](../../coding/cpp/stacks_queues/questions.md). | Solution: [implemented C++](../../coding/cpp/stacks_queues/solutions.md#2-min-stack). Store normal stack plus min stack of current minima, or store pairs `{value, currentMin}`. | Time `O(1)` push/pop/top/min; space `O(n)`. | Store min only on change with counts to reduce memory. | Pair-per-entry is simplest; compressed min stack is more memory efficient but slightly more stateful. |
| 13 | Coding | [Quorum Read/Write Simulator](../../coding/cpp/distributed_systems_algorithms/questions.md). | Solution: [implemented C++](../../coding/cpp/distributed_systems_algorithms/solutions.md#3-quorum-readwrite-simulator). Store versioned values per replica. Write to `W` replicas with incremented version; read from `R` replicas and return highest version, requiring `R + W > N`. | Write `O(W)`; read `O(R)`; space `O(N)`. | Stop after quorum replies; add read repair asynchronously. | Quorums improve availability but may return stale data without careful versioning and repair. |
| 14 | Coding | [Consistent Hashing Ring](../../coding/cpp/distributed_systems_algorithms/questions.md). | Solution: [implemented C++](../../coding/cpp/distributed_systems_algorithms/solutions.md#1-consistent-hashing-ring). Add virtual nodes to an ordered map; key owner is first virtual node clockwise from key hash. | Lookup `O(log V)`; add/remove `O(vnodes log V)`; space `O(V)`. | Sorted vector for read-heavy rings; weighted vnodes for heterogeneous capacity. | Ring is familiar and tunable; rendezvous hashing is simpler for replica choice and avoids ring state. |
| 15 | Coding | [Group Anagrams](../../coding/cpp/hashing/questions.md). | Solution: [implemented C++](../../coding/cpp/hashing/solutions.md#2-group-anagrams). Canonicalize each string by sorted chars or frequency vector; group in hash map from signature to strings. | Sort signature `O(total chars log word length)`; frequency signature `O(total chars)`. | Frequency signature avoids per-word sort for fixed alphabets. | Frequency arrays are fast but alphabet-specific; sorted signatures are simpler and general. |
| 16 | Design | [Design multi-tenant I/O QoS and noisy-neighbor control](../../system_design/apple_l7_system_design_prep.md#25-design-multi-tenant-io-qos-and-noisy-neighbor-control). | Use hierarchical tenant, volume, shard, and node budgets; classify reads/writes/background work; enforce token buckets and priority queues; expose throttling metrics. | Discuss per-request scheduling overhead, queue depth, and device/network saturation. | Separate small reads from large writes; throttle repair/snapshot traffic; split or move hot shards. | Strict limits protect neighbors but waste spare capacity; work-conserving fairness improves utilization but can surprise users. |
| 17 | Coding | [Count Subarrays With Sum K](../../coding/cpp/arrays_strings/questions.md). | Solution: [implemented C++](../../coding/cpp/arrays_strings/solutions.md#4-count-subarrays-with-sum-k). Maintain prefix sum and count of previous prefix sums; for each sum `s`, add `freq[s-k]` to answer. | Time `O(n)` average; space `O(n)`. | Reserve hash map; use 64-bit prefix sums to avoid overflow. | Handles negatives; sliding window is faster/smaller but only works for non-negative values. |
| 18 | Coding | [Course Schedule Order](../../coding/cpp/graphs/questions.md). | Solution: [implemented C++](../../coding/cpp/graphs/solutions.md#1-course-schedule-order). Build graph and indegrees; run Kahn topological sort; if output size is less than courses, cycle exists. | Time `O(V + E)`; space `O(V + E)`. | Compact adjacency vectors; use queue/deque; pre-size indegree. | Kahn gives order and cycle detection; DFS can be shorter but recursion depth can hurt. |
| 19 | Design | [Design a cross-org replication foundation for storage backends](../../system_design/apple_l7_system_design_prep.md#26-design-a-cross-org-replication-foundation-for-storage-backends). | Provide Replication SDK/runtime, membership API, policy store, rollout controller, observability, and repair hooks while allowing backend-specific apply and snapshot formats. | Discuss groups, replicas, log records, rollout waves, and compatibility windows. | Version protocol messages; deterministic simulation; shadow replication; checksum comparison. | Shared foundations reduce duplicated correctness work but can become lowest-common-denominator platforms. |
| 20 | Coding | [Median of Two Sorted Arrays](../../coding/cpp/binary_search/questions.md). | Solution: [implemented C++](../../coding/cpp/binary_search/solutions.md#1-median-of-two-sorted-arrays). Binary search partition in smaller array so left partition max `<=` right partition min; compute median from boundary values. | Time `O(log min(m,n))`; space `O(1)`. | Always search smaller array; avoid copying/slicing. | Elegant and optimal but easy to get boundary cases wrong; merge approach is simpler `O(m+n)`. |
